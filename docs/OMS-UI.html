OMS Backoffice UI

How the screen works. This describes the current FirstDemat backoffice orders portal.

This is an internal screen for operations to inspect parent orders, open their legs on the same page, and cancel an unplaced stop-loss or target. The UI talks only to the OMS worker. It does not place orders, modify prices, cancel an entry, or square off a position.

How the screen is organised

There is one page, titled OMS BackOffice / Parent orders.

The top bar shows whether OMS is live, how many parents are still active, an auto-refresh choice, and a refresh button.

Under that, six count cards sit above a search box, a status dropdown, and a column picker. The parent table fills the rest of the page. Clicking a parent row opens that parent’s legs directly underneath it. Several parents can stay open at once.

Connection

The OMS base URL comes from VITE_OMS_BASE_URL. If that is empty, the UI uses oms_api_url from the browser, then /api/v1/oms.

Calls under that base send X-Internal-Key when VITE_OMS_INTERNAL_KEY or oms_internal_key is set.

GET /health is called about 1.5 seconds after load, then every 20 seconds. A healthy response shows OMS live. Any failure shows OMS offline and a banner that the worker cannot be reached. Health does not use the internal key.

Top bar

Active is the number of parents whose status is not EXITED, CANCELLED, or FAILED. That includes PENDING, PENDING_ENTRY, ENTRY_PLACED, ENTRY_FILLED, SL_ARMED, and PROTECTIVE_ARMED. The count is for the whole book, not the current page.

Auto is 10s, 30s, or 60s. The choice is saved in the browser. It reloads the parent list only. It does not reload legs that are already open.

The refresh button reloads the parent list and any legs that are already open, and it recalculates which Cancel buttons are red.

Count cards

Total parents, Filled, Failed, Exited, and Cancelled come from the parent-list response and cover every parent, including ones not on the current page. They do not change when a status filter or search is applied.

  • Filled is parents in ENTRY_FILLED.
  • Failed is parents in FAILED.
  • Exited is parents in EXITED.
  • Cancelled is parents in CANCELLED.

Armed is different. It is the number of parents on the current page that have at least one leg Cancel can cancel. It is not the count of SL_ARMED or PROTECTIVE_ARMED.

Finding parents

Search waits 350ms after typing, then reloads from the first page. The worker matches the text against user id, client id, OMS order id, segment, instrument id, and entry validity.

The status dropdown filters the table. Choices are ALL plus every parent status, each with its whole-book count: PENDING, PENDING_ENTRY, ENTRY_PLACED, ENTRY_FILLED, SL_ARMED, PROTECTIVE_ARMED, EXITED, CANCELLED, and FAILED. Changing the status returns to page 1.

If a search or status filter returns nothing, Reset All Filters clears both.

Columns

The parent columns are OMS order id, user id, product, segment, instrument id, display name, parent status, entry validity, valid until, created, updated, and Action.

Columns can show or hide each one. Select all and Unselect all apply at once. The choice is saved in the browser. Product and parent status are plain text.

If every column is hidden, the table says No columns selected and a row click does not open legs.

The OMS order id can be copied. The copy control does not open the row.

Parent table

The default page size is 25. The footer can switch to 15, 25, 50, or 100 rows and move to the first, previous, next, or last page. The footer shows which records are on screen.

A second refresh control on the filter bar reloads the parent list only. It does not reload open legs. The top-bar refresh does both.

Parent status is not used to hide a row or to block Cancel.

Opening legs

Clicking a parent row loads GET /backoffice/orders/leg?oms_order_id= once and draws the legs under that row. Clicking the same parent row again closes it. Clicking a leg row closes only that parent. Other open parents stay open.

The legs table does not repeat the OMS order id. Its columns are leg id, Symphony id, role, status, side, type, quantity, filled quantity, limit price, trigger price, stop price, segment, instrument id, trail points, peak LTP, TP points, limit offset, armed at, fired at, created, and updated.

While the legs are loading, the row says Loading legs. If the parent has none, it says No legs found. An error is shown in that same row.

Open legs stay as they were at the click. They reload when the top-bar refresh is used, when the row is closed and opened again, or after a successful cancel.

To colour the Cancel buttons, the page also requests legs once for every parent currently listed. That scan is separate from opening a row.

Cancel

Every parent row has a Cancel button in the Action column, as long as that column is visible. The button does not open the legs.

The button is red when that parent has at least one leg that can be cancelled. Otherwise it stays indigo. Opening an indigo row’s popup says No legs can be cancelled for this order.

A leg can be cancelled only when all three are true:

  • Its role is SL or TARGET. The entry leg cannot be cancelled here.
  • Its status is PENDING or ARMED.
  • Its Symphony id is empty or 0.

OMS does not require a particular parent status. The parent must exist, and the user id and client id sent with the cancel must match that parent.

The popup is titled with the OMS order id. It lists only the legs that pass the three checks, with leg id, role, and status. A header checkbox selects or clears every listed leg. One leg or several can be ticked. A reason is required. The Cancel button in the popup stays disabled until at least one leg is ticked.

Confirming sends one POST /orders/smart-intraday/cancel-protective per selected leg, in order. The body is appOrderID set to OMSLEG-{leg id}, plus clientID and userID. This updates the leg to CANCELLED inside OMS. It does not send the cancel to Symphony.

After each of those calls succeeds, the screen sends POST /backoffice/audit/log with event type OPERATOR_CANCEL_LEG, the parent id, the leg id, the reason, actor BACKOFFICE_OPERATOR, and the user id. The audit call is what stores the reason. If the audit call fails, the error is shown and any later selected legs are not sent. The leg whose cancel already succeeded stays cancelled.

On success, a toast names the cancelled leg, or says how many were cancelled. The toast closes itself after 4.5 seconds, or the operator can dismiss it. The parent list reloads, open legs reload, and the popup loads the remaining cancellable legs.

APIs this screen calls

All of these, except health, are under the configured OMS base and send X-Internal-Key when a key is set.

  • GET /health shows OMS live or offline.
  • GET /backoffice/orders loads the parent table, pagination, and the status counts. Search, status, page, page size, and auto-refresh use this call. Query fields are page, limit, status, and search.
  • GET /backoffice/orders/leg?oms_order_id= loads one parent’s legs. It is used for the red Cancel check, for an opened row, for the cancel popup, and when open legs are refreshed.
  • POST /orders/smart-intraday/cancel-protective cancels one unplaced protective leg.
  • POST /backoffice/audit/log stores the reason after that cancel succeeds.

getProtectives is still in the API client and is not used by this screen.
